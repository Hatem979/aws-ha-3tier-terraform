# Monitoring Module

## Overview

The Monitoring Module provides centralized observability for the AWS three-tier architecture using Amazon CloudWatch and Amazon SNS.

It monitors key application load balancer metrics, application target health, Auto Scaling Group capacity, and Amazon RDS performance indicators.

The module also creates CloudWatch alarms that can publish notifications to an SNS topic when configured thresholds are breached.

## Resources Created

| Resource | Purpose |
|---|---|
| CloudWatch Dashboard | Displays key metrics for the ALB, application targets, ASG, and RDS. |
| ALB 5XX Alarm | Detects elevated HTTP 5XX errors generated by the load balancer. |
| Target 5XX Alarm | Detects elevated HTTP 5XX errors returned by application targets. |
| RDS CPU Alarm | Detects sustained high database CPU utilization. |
| RDS Storage Alarm | Detects low available database storage. |
| ASG Capacity Alarm | Detects when the number of InService instances falls below the configured minimum. |
| SNS Topic | Provides a notification destination for CloudWatch alarms. |
| SNS Email Subscription | Optionally delivers notifications to a confirmed email address. |

## Monitoring Strategy

### Application Load Balancer

The module monitors incoming request counts and load-balancer-generated HTTP 5XX errors.

A separate alarm tracks HTTP 5XX errors returned by application targets, helping distinguish load-balancer issues from application-level failures.

### Application Health

The dashboard displays healthy and unhealthy target counts.

The Auto Scaling Group alarm monitors the number of instances in the InService state. This helps identify situations where the application tier has fewer healthy instances than expected.

### Database Monitoring

The module monitors RDS CPU utilization and available storage.

These metrics provide early warning of resource pressure and help guide troubleshooting before database performance becomes severely degraded.

### Notifications

CloudWatch alarms publish notifications to an SNS topic when they enter the ALARM state.

An email subscription can be configured through the module's `alarm_email` input. The recipient must confirm the subscription before receiving notifications.

## Design Considerations

- Alarm thresholds should be adjusted to match workload characteristics and operational requirements.
- Missing metric data does not always mean that a service is healthy.
- CloudWatch alarms complement, but do not replace, application logs, distributed tracing, and active health checks.
- Dashboard metrics and alarms may not show useful data until the associated resources are running and emitting metrics.
- Additional metrics may require different dimensions or additional configuration.

## Deployment and Validation

Run Terraform formatting, validation, and planning from the root environment:

```bash
terraform -chdir=environments/dev fmt -recursive
terraform -chdir=environments/dev validate
terraform -chdir=environments/dev plan
```

Review the plan before applying changes. CloudWatch dashboards, alarms, SNS notifications, and associated metric usage may incur charges depending on the configuration and usage.

## Design Rationale

This module separates monitoring and alerting from the core infrastructure modules.

It provides a reusable foundation for operational visibility and can be extended with application logs, log retention policies, composite alarms, additional service metrics, and automated incident-response workflows.
